# MailWhere v0.13.0 — Qwen/Qwen3.8-27B and bundled skill hardening

## Changed

- Corrects the release target to `Qwen/Qwen3.8-27B`. Use this 27B target only for release configuration and operator guidance.
- Makes LLM compatibility fail closed: analysis and LLM-backed waiting-closure judgment require a successful probe that uses MailWhere's real single-item, batch, and waiting-closure request shapes.
- Keeps JSON Schema as the default structured-output mode and exposes JSON Object only as a weaker compatibility mode.
- Adds explicit thinking controls for Qwen3.8 endpoints:
  - prefer template-native `chat_template_kwargs: { "enable_thinking": false }`;
  - serve Qwen3.8 with vLLM `>=0.17.0` and `--reasoning-parser qwen3`;
  - on vLLM `0.25+`, `reasoning_effort="none"` can be used as a convenience path only after the probe validates it.
- Preserves LLM concurrency at `1/1`. Failed or partial batches may retry missing items one at a time, but MailWhere must not start parallel LLM requests.
- Clarifies review backlog counts as three separate numbers: total unresolved review items, visible page count capped at 100, and retryable LLM failures.
- Bundles a read-only MailWhere skill for Codex and Claude portable users, with a fixed repair policy: **Yes** overwrites the bundled install without backup; **No** preserves the current folder and opens it.
- Adds a body-free original-open path for automation: CLI/skill/exported normal outputs may expose only an opaque `open_source_token`; raw StoreID, EntryID, source id, and source hash stay hidden from those surfaces.

## Operator notes

### vLLM endpoint

Start from the official Qwen3.8 vLLM recipe, then keep MailWhere's settings conservative:

```bash
vllm serve Qwen/Qwen3.8-27B \
  --max-model-len 262144 \
  --reasoning-parser qwen3
```

This command must be verified on the target GPU/vLLM host. This Linux checkout can verify documentation and packaging shape, but it cannot prove the live endpoint behavior.

Use the exact model ID exposed by `/v1/models` in MailWhere settings. If the server exposes FP8/NVFP4 model IDs instead, select that returned ID rather than inventing one.

### Probe requirement

The Settings connection test is no longer only a small JSON ping. Before follow-up analysis runs, MailWhere must validate:

1. a synthetic single-mail analysis response;
2. a synthetic batch response with matching `items[]`/`contents[]` ids;
3. a synthetic waiting-closure response through the normal closure parser;
4. selected thinking control and structured-output mode;
5. no thinking leakage, reasoning metadata, Responses incomplete state, truncation, missing ids, invalid JSON, or schema mismatch.

Changing provider, normalized endpoint, model, thinking-control mode, structured-output mode, temperature, max-output-token policy, or batch-size policy invalidates the saved proof and requires a new successful probe.

LLM-backed waiting-closure judgment uses the same current probe proof gate before it can call the endpoint. The connection test includes a third synthetic waiting-closure probe under that same proof; if the proof is missing or stale, closure judgment stays on deterministic rules.

### Skill install and repair

See [`../SKILL_INSTALL.md`](../SKILL_INSTALL.md). The bundled skill is offline and read-only. It reads sanitized CLI/provider output and only opens an original mail when the user explicitly asks it to call:

```powershell
.\MailWhere.exe --open-source-token <token>
```

The token is opaque and resolved locally by MailWhere. This Windows-only command is the only supported Skill launch path for original-open and must be smoke-tested with Classic Outlook on the target PC. The skill must not perform Outlook COM automation and must not display raw StoreID/EntryID. Internal WPF/Outlook adapter code may retain raw locator values inside the trusted local process/database boundary; those values are not exported API fields.

## Verification

Automated release verification should run in this order:

```bash
dotnet test MailWhere.sln
dotnet build MailWhere.sln --no-restore
scripts/verify-static.sh
scripts/publish-portable.sh
```

Then inspect the portable ZIP for:

- `docs/releases/v0.13.0.md`;
- copied `skills/mailwhere/**` bundle;
- no `.omx` runtime files;
- no SQLite databases, mailbox exports, API keys, prompt logs, or raw-mail artifacts.
